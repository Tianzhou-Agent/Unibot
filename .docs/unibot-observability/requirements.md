# IR-01 平台运行可观测与质量分析

## 1. 需求名称

Agent 运行可观测、性能分析与错误诊断能力。

## 2. 利益相关方

- Agent 开发人员
- 平台研发人员
- 测试人员
- 运维及 SRE 人员
- Agent 产品负责人
- 模型及工具服务负责人

## 3. 业务背景

当前 Agent 平台中的一次用户请求，通常会经过 Agent 编排、模型调用、工具调用、知识检索及内部服务处理等多个环节。

由于缺少统一的调用链、性能指标和错误数据，当前存在以下问题：

1. 用户请求失败后，无法快速确定问题发生在 Agent、模型、工具还是平台服务。
2. 错误信息、调用链和原始日志相互割裂，排查过程中需要跨系统检索。
3. 无法量化不同 Agent、模型和工具的性能、稳定性及资源消耗。
4. 缺少统一的数据口径，模型耗时、Agent 耗时、Token 消耗等指标难以横向比较。
5. Agent 版本或模型配置变更后，无法快速判断其对性能和成功率的影响。

## 4. 当前问题

- 缺少用户请求级的端到端 Trace。
- Agent、模型和工具调用关系不可见。
- 错误无法定位到具体调用节点。
- 原始日志无法通过 Trace 或 Span 关联。
- 模型首 Token 时延和 Token 消耗无法统一统计。
- Agent 单轮耗时、调用次数和重试次数缺少统计。
- 工具调用成功率、超时率和耗时缺少分析。
- 不同 Agent、模型、工具和版本之间无法进行性能对比。

## 5. 需求目标

建设统一的 Agent 运行可观测与质量分析能力，使平台能够：

1. 记录一次用户请求从进入平台到最终响应结束的完整调用过程。
2. 展示 Agent、模型、工具及内部服务之间的调用关系。
3. 在错误发生后定位到具体 Trace 和 Span。
4. 将错误、调用链和原始日志统一关联。
5. 统计 Agent、模型和工具的性能、稳定性及资源消耗指标。
6. 支持按照 Agent、版本、模型、工具、租户、用户和时间范围进行分析。
7. 为 Agent 优化、模型选型、工具治理和线上问题排查提供数据依据。

## 6. 用户场景

### 场景一：线上错误排查

作为 Agent 开发人员，我需要从错误记录进入对应调用链，并定位到具体异常节点，以快速判断问题来自模型、工具、Agent 编排还是平台服务。

### 场景二：性能瓶颈分析

作为平台负责人，我需要查看 Agent 单轮耗时及各调用节点耗时，以识别模型调用、工具调用或平台处理中的性能瓶颈。

### 场景三：模型体验评估

作为模型负责人，我需要查看模型首 Token 时延、总响应耗时、Token 消耗和调用成功率，以评估不同模型的体验和成本。

### 场景四：工具质量治理

作为工具负责人，我需要查看工具调用次数、成功率、错误率、超时率和耗时，以识别不稳定或低性能工具。

### 场景五：版本变更验证

作为 Agent 产品负责人，我需要对比不同 Agent 版本的成功率、耗时、Token 消耗和错误分布，以评估版本变更效果。

## 7. 业务价值

- 降低线上问题平均定位时间。
- 提升 Agent、模型和工具问题的可诊断性。
- 建立统一的 Agent 运行质量评价体系。
- 支持 Agent 性能优化和模型选型。
- 降低无效 Token 消耗和模型调用成本。
- 提高工具治理和服务稳定性。
- 为版本发布和容量规划提供数据支撑。

## 8. 成功指标

建议首期使用以下指标衡量 IR 是否实现：

| 指标               | 目标建议                                      |
| ------------------ | --------------------------------------------- |
| Trace 覆盖率       | 不低于 95% 的有效用户请求生成完整 Trace       |
| 错误关联率         | 不低于 90% 的执行错误关联 trace_id 和 span_id |
| 错误节点定位率     | 不低于 90% 的错误可定位到具体调用节点         |
| 日志关联率         | 不低于 90% 的异常 Span 可查看关联日志         |
| 核心指标采集完整率 | TTFT、耗时、Token 等字段完整率不低于 95%      |
| 数据查询时效       | 明细数据在请求完成后 1 分钟内可查询           |
| 聚合指标时效       | 分析指标延迟不超过 5 分钟                     |
| 调用链查询性能     | 常规查询结果 3 秒内返回                       |
| 问题定位效率       | 常见线上问题定位时间显著下降                  |

具体数值应结合现有技术架构、流量规模和数据保留策略确认。

## 9. 需求范围

### 本期范围

- 用户请求级 Trace 生成与透传
- Agent、模型、工具 Span 采集
- 调用链查询和详情展示
- 节点输入、输出、状态和耗时展示
- 错误中心
- 错误到 Trace、Span 的跳转
- 原始日志关联和查看
- Agent 运行分析
- 模型性能和 Token 分析
- 工具调用分析
- 平均值、P50、P95、P99 等性能统计
- Agent、模型、工具和版本维度筛选
- 数据权限及敏感信息脱敏

### 非本期范围

- 基于大模型的自动根因分析
- 自动修复 Agent 配置或代码
- 完整告警平台建设
- 模型回答内容质量自动评测
- Agent A/B 实验平台
- 成本预算和配额控制
- 跨企业、跨平台的全链路追踪

## 10. 边界约束

1. 调用链采集失败不得阻塞 Agent 主业务流程。
2. 输入输出中的用户隐私、密钥和敏感字段必须脱敏。
3. 用户只能查看其有权限访问的租户、Agent 和调用数据。
4. 超大 Prompt、模型输出和工具响应应支持摘要存储或外部存储。
5. Trace、Span、错误和日志之间必须使用统一标识关联。
6. 流式模型调用必须明确首 Token 时间和响应结束时间。
7. 重试、并行工具调用和嵌套 Agent 调用必须能够正确表达。
8. 指标定义必须在平台内统一，不允许不同页面使用不同计算口径。

## 11. 核心对象

| 对象         | 定义                                           |
| ------------ | ---------------------------------------------- |
| User Request | 用户发起的一次消息或 API 请求                  |
| Trace        | 一次用户请求的完整端到端执行链路               |
| Span         | Trace 中的一次 Agent、模型、工具或内部处理活动 |
| Agent Span   | 一次 Agent 执行实例                            |
| Model Span   | 一次模型请求及响应                             |
| Tool Span    | 一次工具调用及响应                             |
| Error Event  | 执行过程中产生的标准化异常记录                 |
| Raw Log      | 与 Trace 或 Span 关联的原始日志                |
| Metric       | 基于调用明细计算的统计指标                     |

## 12. 核心指标口径

### Agent 单轮耗时

Agent 单轮耗时等于最终响应结束时间减去平台收到用户请求时间。

### 模型首 Token 时延

TTFT 等于收到首个有效输出 Token 的时间减去模型请求发起时间。

### 模型总耗时

模型总耗时等于模型响应结束时间减去模型请求发起时间。

### 工具调用耗时

工具调用耗时等于工具调用结束时间减去工具调用发起时间。

### 请求成功率

请求成功率等于成功完成的用户请求数除以有效用户请求总数。

### Token 消耗

Token 消耗应分别统计输入 Token、输出 Token、缓存 Token及总 Token；如模型供应商支持，还应记录推理 Token。

## 14. 验收原则

IR-01 完成的最低闭环为：

用户发起 Agent 请求后，系统能够生成完整 Trace；当某个模型或工具调用失败时，错误中心能够查询该错误，用户可以进入对应 Trace，自动定位异常 Span，并查看经过脱敏的输入输出、错误信息和关联日志。同时，平台能够在分析页面统计对应 Agent、模型和工具的耗时、成功率及 Token 指标。

# IR-02 用户体验反馈与运营增长分析

## 1. 需求名称

Agent 用户反馈闭环与用户运营分析能力。

## 2. 利益相关方

- Agent 最终用户
- 产品经理
- Agent 运营人员
- Agent 负责人
- 客户成功人员
- 数据分析人员
- 企业或租户管理员

## 3. 业务背景

当前平台主要关注 Agent 是否能够正常执行，但缺少对用户主观体验和持续使用情况的分析。

即使 Agent 请求成功，也可能存在回答不准确、未解决问题、响应速度慢、工具调用结果不符合预期等情况。与此同时，平台缺少统一的用户活跃、请求量、渗透率和留存指标，无法判断 Agent 是否真正被用户采用并形成持续使用。

因此，需要建立用户反馈和运营数据闭环，将用户主观评价、具体请求、调用链和用户行为数据关联起来。

## 4. 当前问题

- 用户无法对单轮回答进行结构化评价。
- 点赞点踩无法关联到具体请求和调用链。
- 点踩原因缺少统一分类。
- 用户反馈缺少处理状态和责任人。
- 无法统计点赞率、点踩率和反馈原因。
- DAU、WAU、MAU 等活跃指标缺少统一口径。
- 用户请求数和人均请求数无法统一分析。
- Agent 渗透率的分子和分母定义不明确。
- 缺少 D1、D7、D30 留存及 Cohort 分析。
- 反馈数据和用户行为数据未形成统一分析视图。

## 5. 需求目标

建设统一的用户体验反馈与运营增长分析能力，使平台能够：

1. 支持用户对单轮 Agent 回答进行点赞、点踩和补充反馈。
2. 将用户反馈自动关联到用户、会话、请求、Agent 和调用链。
3. 支持 Agent 负责人查看、分类和处理反馈。
4. 分析用户反馈率、点赞率、点踩率及主要问题原因。
5. 统一统计用户活跃度、请求量、渗透率和留存率。
6. 支持按 Agent、租户、部门、用户类型和时间维度分析。
7. 识别高价值 Agent、低采用 Agent和用户流失问题。
8. 为 Agent 产品优化和运营策略提供数据支撑。

## 6. 用户场景

### 场景一：用户快速反馈

作为 Agent 用户，我需要对某次回答点赞或点踩，并快速说明问题原因，以表达本次使用体验。

### 场景二：反馈问题回溯

作为 Agent 负责人，我需要从用户反馈进入对应对话和调用链，以确认问题来自回答质量、模型性能、工具调用还是 Agent 编排。

### 场景三：反馈处理闭环

作为产品或运营人员，我需要对负面反馈设置状态、负责人和处理结论，以跟踪问题处理情况。

### 场景四：活跃度分析

作为平台负责人，我需要查看 DAU、WAU、MAU 和用户使用趋势，以判断平台整体活跃情况。

### 场景五：Agent 渗透分析

作为 Agent 产品负责人，我需要查看有权限用户中实际使用 Agent 的用户比例，以判断 Agent 的采用程度。

### 场景六：用户留存分析

作为运营人员，我需要查看新用户 D1、D7、D30 留存和 Cohort 留存，以识别用户是否持续使用平台。

### 场景七：反馈与行为关联

作为产品经理，我需要比较不同 Agent 的请求量、留存率和用户满意度，以判断哪些 Agent 真正创造了用户价值。

## 7. 业务价值

- 建立从用户评价到技术问题定位的完整闭环。
- 识别回答质量、性能和功能体验中的主要问题。
- 提高负面反馈处理效率。
- 统一用户增长和运营指标口径。
- 准确评估平台和 Agent 的真实采用情况。
- 识别高活跃用户、低活跃用户和流失用户。
- 支持 Agent 推广、优化和下线决策。
- 为产品迭代优先级提供量化依据。

## 8. 成功指标

| 指标               | 目标建议                                       |
| ------------------ | ---------------------------------------------- |
| 反馈关联完整率     | 不低于 95% 的反馈可关联 request_id 和 trace_id |
| 反馈提交成功率     | 不低于 99%                                     |
| 反馈重复提交控制   | 同一用户同一回答仅保留一个有效评价             |
| 反馈问题回溯率     | 不低于 90% 的负面反馈可回溯调用链              |
| 活跃指标数据完整率 | 不低于 99%                                     |
| 用户事件采集成功率 | 不低于 99%                                     |
| 运营指标时效       | 延迟不超过约定周期，如 T+1 小时或 T+1 天       |
| 指标口径一致性     | 不同页面和导出结果使用统一口径                 |
| 用户身份识别率     | 有效请求中的用户身份识别率达到约定目标         |

点赞率和留存率本身不适合在首期直接设固定提升值，因为它们受到 Agent 内容质量和业务场景影响。首期应优先保证数据完整、口径统一和问题可回溯。

## 9. 需求范围

### 本期范围

- 单轮回答点赞和点踩
- 点踩原因选择
- 文字补充反馈
- 反馈与用户、会话、请求、Agent、Trace 的关联
- 反馈列表和反馈详情
- 反馈状态、负责人和处理结果
- 从反馈跳转到对话及调用链
- 点赞率、点踩率和反馈率分析
- 反馈原因分布分析
- DAU、WAU、MAU 和 DAU/MAU
- 用户请求总数及人均请求数
- 用户渗透率
- D1、D7、D30 留存
- 周 Cohort 和月 Cohort
- Agent、租户、部门及用户类型维度筛选

### 非本期范围

- 自动生成用户反馈回复
- 自动关闭或自动修复反馈问题
- 基于情感模型的全量对话情绪分析
- 用户画像推荐系统
- 精细化营销和消息触达平台
- 商业化计费分析
- 全功能客户工单系统
- 因果分析和增长实验平台

## 10. 边界约束

1. 用户反馈必须绑定具体回答，而不是只绑定整个会话。
2. 同一用户对同一回答重复操作时，应更新原有评价，而不是重复计数。
3. 匿名用户和登录用户应采用不同身份识别规则。
4. 用户活跃必须基于有效行为，而不能仅以访问页面作为活跃标准。
5. 渗透率必须明确权限用户分母来源。
6. 留存率必须明确首次使用时间、观察窗口和回访行为。
7. 删除用户或账号合并后，历史指标处理方式必须明确。
8. 用户隐私数据必须遵循权限和脱敏要求。
9. 反馈内容应防止脚本、敏感信息和恶意输入。
10. 反馈记录与调用链数据保留周期不一致时，应向用户提示数据已过期。

## 11. 核心对象

| 对象            | 定义                                        |
| --------------- | ------------------------------------------- |
| Feedback        | 用户对某次 Agent 回答的评价                 |
| Feedback Reason | 用户反馈的结构化原因                        |
| Feedback Case   | 对负面反馈形成的处理记录                    |
| User Event      | 用户使用平台过程中产生的有效行为事件        |
| Active User     | 统计周期内产生至少一次有效请求的去重用户    |
| New User        | 首次产生有效请求的用户                      |
| Eligible User   | 在统计周期内有权限使用平台或某 Agent 的用户 |
| Retained User   | 在规定观察窗口内再次产生有效行为的用户      |
| Cohort          | 按首次使用日期或周期划分的用户群体          |

## 12. 核心指标口径

### 反馈率

反馈率等于产生点赞或点踩的回答数除以可反馈回答总数。

### 点赞率

建议同时保留两个口径：

- 点赞率一：点赞数除以全部有效反馈数。
- 点赞率二：点赞数除以全部可反馈回答数。

页面必须清楚标明所使用的口径。

### 活跃用户

活跃用户定义为统计周期内至少完成一次有效 Agent 请求的去重用户。

### 人均请求数

人均请求数等于有效用户请求总数除以活跃用户数。

### Agent 用户渗透率

Agent 用户渗透率等于统计周期内使用过该 Agent 的去重用户数，除以统计周期内有权限使用该 Agent 的去重用户数。

### D7 留存率

D7 留存率等于首次使用后第 7 天再次产生有效请求的新用户数，除以对应日期的新增用户数。

应另外明确使用自然日留存、滚动留存还是区间留存。

## 14. 验收原则

IR-02 完成的最低闭环为：

用户能够对某次 Agent 回答提交点赞或点踩；负面反馈能够选择原因并补充说明；反馈记录能够关联用户、会话、请求、Agent 和 Trace；Agent 负责人能够查看反馈、回溯调用链并记录处理结果。同时，平台能够统一统计 DAU、MAU、请求量、Agent 渗透率和用户留存指标。

# 两个 IR 的关系

IR-01 负责回答：

- 系统发生了什么？
- 哪个节点出现问题？
- 哪个 Agent、模型或工具性能较差？
- 一次请求消耗了多少时间和资源？

IR-02 负责回答：

- 用户是否满意？
- 哪类问题最影响用户体验？
- 用户是否实际采用 Agent？
- 用户是否持续使用平台？

两个 IR 通过以下对象形成关联：

| IR-02 对象       | 关联 IR-01 对象              |
| ---------------- | ---------------------------- |
| 用户反馈         | request_id、trace_id         |
| 点踩原因         | 错误类型、性能指标、调用节点 |
| 用户请求         | Trace                        |
| Agent 使用行为   | Agent Span                   |
| 响应慢反馈       | Agent 耗时、TTFT             |
| 工具结果错误反馈 | Tool Span                    |
| 回答错误反馈     | Model Span、Agent Span       |

最终形成闭环：

用户产生请求 → IR-01 记录完整运行过程 → 用户提交反馈 → IR-02 记录用户体验 → 负责人从反馈回溯 IR-01 调用链 → 根据问题优化 Agent、模型或工具。
