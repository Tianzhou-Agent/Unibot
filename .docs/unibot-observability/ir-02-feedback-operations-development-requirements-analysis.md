# IR-02 用户体验反馈与运营增长分析——开发需求分析

## 1. 文档说明

### 1.1 文档目的

本文档针对原始需求中的“IR-02 用户体验反馈与运营增长分析”，结合 Unibot 当前实现，形成可独立评审和开发的需求分析。

本文档回答：

1. 当前项目有哪些可以支持反馈关联和用户运营的基础数据。
2. 当前实现与 IR-02 各项 SR 的差距。
3. 用户反馈闭环和运营分析需要建设哪些能力。
4. IR-02 对身份体系、组织权限数据和 IR-01 的依赖。
5. 各开发阶段和验收标准。

本文档不包含 IR-01 的 Trace/Span 详细实现、数据库 DDL、完整 API Schema、详细技术设计和工期估算。

### 1.2 需求范围

本需求覆盖：

- 对具体 Assistant Message 点赞和点踩
- 点踩原因和文字补充
- 反馈与用户、会话、请求、Agent 和 Trace 的关联
- 重复反馈控制
- 反馈查询和反馈处理闭环
- 从反馈回溯对话和调用链
- 反馈率、点赞率、点踩率和原因分布
- DAU、WAU、MAU 和 DAU/MAU
- 用户请求数和人均请求数
- 平台及 Agent 用户渗透率
- D1、D7、D30 留存
- 周 Cohort 和月 Cohort
- Agent、租户、部门、用户类型和时间维度分析
- 用户数据权限和隐私保护

### 1.3 非本期范围

- 自动生成用户反馈回复
- 自动关闭或自动修复反馈问题
- 全量对话情感分析
- 用户画像推荐系统
- 精细化营销和消息触达
- 商业化计费分析
- 全功能客户工单系统
- 因果分析和增长实验平台
- IR-01 的 Trace/Span 采集和性能分析实现

### 1.4 优先级

| 优先级 | 定义 |
| --- | --- |
| P0 | 身份、数据口径、权限或依赖阻塞项 |
| P1 | 用户反馈和基础运营最小闭环必须具备 |
| P2 | 留存、Cohort 和高级关联分析 |
| P3 | 后续体验优化 |

## 2. 业务目标和使用场景

### 2.1 业务目标

IR-02 需要让平台能够回答：

- 用户是否满意某次 Agent 回答。
- 哪些问题最影响用户体验。
- 负面反馈是否得到处理。
- 用户是否真正使用某个 Agent。
- 用户是否持续使用平台和 Agent。
- 哪些 Agent 具有高请求量、高满意度和高留存。
- 哪些 Agent 存在低采用、低满意度或用户流失问题。

### 2.2 核心场景

#### 场景一：用户快速反馈

用户对某次回答点赞或点踩，并快速选择原因或填写补充说明。

#### 场景二：反馈问题回溯

Agent 负责人从反馈进入原对话和调用链，判断问题来自回答质量、模型性能、工具调用还是 Agent 编排。

#### 场景三：反馈处理闭环

产品或运营人员为负面反馈设置状态、负责人和处理结论，并保留操作记录。

#### 场景四：活跃度分析

平台负责人查看 DAU、WAU、MAU 和用户使用趋势。

#### 场景五：Agent 渗透分析

Agent 负责人查看有权限用户中实际使用该 Agent 的用户比例。

#### 场景六：用户留存分析

运营人员查看新增用户 D1、D7、D30 和 Cohort 留存。

#### 场景七：反馈与行为关联

产品经理比较不同 Agent 的请求量、满意度、渗透率和留存。

## 3. 当前项目能力分析

### 3.1 消息和反馈关联基础

当前 Conversation Message 已包含：

- `id`
- `role`
- `content`
- `trace_id`
- 创建时间

ChatResponse 已包含：

- `conversation_id`
- `message_id`
- `trace_id`
- 状态

可以复用：

- Assistant Message ID 可以作为反馈绑定对象。
- Trace ID 可以支持从反馈回溯调用链。
- Conversation ID 可以支持返回原对话。

主要问题：

- 当前没有明确的 `request_id`。
- Feedback 是否绑定 Assistant Message ID 需要冻结为正式规则。
- 历史消息删除或会话删除后，Feedback 如何展示尚未定义。

### 3.2 用户和租户基础

当前 Conversation、Chat、Trace、AINA Installation 等对象中已有：

- `user_id`
- `tenant_id`

可以复用：

- 作为 Feedback 和 User Event 的基础维度。
- 作为租户隔离字段。

主要问题：

- 用户和租户仍可由客户端参数提供，不是完全可信身份。
- 前端当前固定使用 `anonymous/default`。
- 匿名用户没有稳定身份规则。
- 没有账号合并和用户删除策略。

### 3.3 Agent 和使用行为基础

当前项目已经存在：

- AINA ID 和版本
- AINA Installation
- Conversation 中的 Primary、Active 和 Last AINA
- Trace 中的能力调用信息
- Chat 请求和完成状态

可以复用：

- 推导一次请求使用了哪些 AINA。
- 建立 Agent 使用事件。
- 关联 Agent 版本。

主要问题：

- 原始需求中的 Agent 是否等同于 AINA 尚未明确。
- 一次请求涉及多个 AINA 时，Agent 使用归属规则未定义。
- AINA Installation 表示用户安装，不一定等同于“有权限使用”。
- 缺少权限用户的周期快照。

### 3.4 请求和活跃行为基础

当前每次 Chat 会生成 Trace，并保存：

- 用户
- 租户
- 会话
- 请求时间
- 完成状态

可以复用：

- 作为有效请求事件的来源。
- 计算基础请求量和活跃用户。

主要问题：

- Trace 是可变业务记录，不是专门的不可变用户事件。
- 有效请求、失败请求、取消请求和审批中请求的口径未冻结。
- 定时任务、Debug 调用和非用户触发请求是否计入运营指标未定义。
- Trace 当前存储和查询方式不适合长期运营聚合。

### 3.5 反馈能力

当前项目没有：

- Feedback 数据模型
- 点赞点踩接口
- 反馈原因字典
- 反馈管理页面
- Feedback Case
- 反馈状态、负责人和处理结论
- Feedback 操作历史

结论：

- Feedback 模块需要从零建设。
- 现有 Message、Conversation 和 Trace 标识可以复用。

### 3.6 运营维度基础

当前已有：

- 用户
- 租户
- AINA/Agent 基础标识
- 请求时间和状态

当前缺少：

- 部门
- 用户类型
- 组织层级
- 平台权限用户
- Agent 权限用户
- 权限生效和失效时间
- 用户首次使用时间
- 用户事件事实表
- 留存 Cohort

结论：

- DAU、请求量可以在身份和事件口径明确后较早建设。
- Agent 渗透率不能只使用 AINA Installation 作为分母。
- 留存和 Cohort 需要专门的用户事件和聚合模型。

### 3.7 权限和隐私基础

当前已有 `RequestActor` 模型和 Trace 脱敏工具。

可以复用：

- 可信身份接入后的统一 Actor。
- 对反馈文字和用户身份实施脱敏的基础工具。

主要问题：

- 当前 API 尚未形成统一可信身份边界。
- 没有 Agent 负责人、运营和租户管理员角色。
- 没有 Feedback 数据访问规则。
- 没有 Feedback 文字内容的脚本、恶意输入和敏感信息处理。

### 3.8 前端基础

当前 Chat 页面已经按 Assistant Message 渲染消息，可以增加反馈入口。

当前 Debug 页面已经支持通过 Trace ID 查看调用信息，可以作为 Feedback 回溯目标。

主要问题：

- 没有点赞点踩组件。
- 没有反馈原因和补充说明交互。
- 没有反馈管理和处理页面。
- 没有运营分析页面。
- 没有图表和 Cohort 展示组件。

## 4. 与 IR-01 的依赖关系

IR-02 不负责建设 Trace/Span，但依赖 IR-01 提供稳定的技术诊断数据。

| IR-02 能力 | 依赖 IR-01 |
| --- | --- |
| Feedback 关联 | 稳定的 `request_id`、`trace_id` |
| Feedback 回溯 | Trace 详情查询和访问权限 |
| 自动定位问题节点 | `span_id` 和异常 Span |
| 响应慢反馈分析 | Agent 耗时和 TTFT |
| Tool 结果错误分析 | Tool Span |
| 回答错误分析 | Model Span 和 Agent Span |
| 反馈与技术指标关联 | Agent、模型、Tool 和版本维度 |

IR-02 可以在以下 IR-01 条件具备后开始反馈闭环：

1. `message_id`、`request_id` 和 `trace_id` 关系稳定。
2. Trace 可以按权限查询。
3. Feedback 保存的 Trace 关联不会因后续数据模型变化而失效。

IR-02 的 DAU、请求量等运营指标不必等待 IR-01 全部性能页面完成，但必须共享统一的有效请求和身份口径。

## 5. 总体结论

当前项目具备 Message、Conversation、Trace、用户、租户和 AINA 等基础标识，适合建设 Feedback 关联，但 IR-02 的业务功能本身基本尚未实现。

IR-02 应拆成两个相对独立的子域：

1. 用户反馈闭环：Feedback 提交、查询、处理和技术回溯。
2. 运营增长分析：用户事件、活跃、请求量、渗透、留存和 Cohort。

其中：

- 用户反馈闭环可以在稳定标识和权限能力完成后优先交付。
- DAU 和请求量依赖可信用户身份与有效请求事件。
- Agent 渗透率依赖外部权限用户清单。
- 留存和 Cohort 依赖首次使用、观察窗口和回访行为口径。

## 7. 开发需求拆分

### 7.1 阶段 A：身份、口径和依赖准备

#### IR02-DR-FND-001 可信用户身份

- 优先级：P0
- 对应：SR-SEC-003、SR-OPS-001
- 工作内容：
  - 登录用户从可信认证上下文获取身份。
  - 定义匿名用户识别规则。
  - 明确同一用户跨会话和跨设备的识别边界。
- 验收：
  - 用户不能通过修改请求参数冒充其他用户。
  - 同一匿名身份在约定周期内可以稳定去重。

#### IR02-DR-FND-002 Agent 归属和权限用户

- 优先级：P0
- 对应：SR-OPS-004、SR-OPS-007
- 工作内容：
  - 明确 Agent 与 AINA 的关系。
  - 明确一次多 AINA 请求的使用归属。
  - 接入平台和 Agent 权限用户来源。
  - 保存统计周期需要的权限用户快照。
- 验收：
  - 每个渗透率结果能够追溯分母来源和统计周期。

#### IR02-DR-FND-003 反馈原因和处理流程

- 优先级：P0
- 对应：SR-FBK-002、SR-FBK-007
- 工作内容：
  - 定义正向和负向反馈原因。
  - 定义 Feedback Case 状态。
  - 定义负责人来源、处理结论和关闭规则。
- 验收：
  - 原因字典和状态流转通过产品、运营和 Agent 负责人评审。

#### IR02-DR-FND-004 运营指标字典

- 优先级：P0
- 对应：SR-OPS-008
- 工作内容：
  - 定义有效请求、活跃、新用户和权限用户。
  - 定义反馈率和两种点赞率。
  - 定义 DAU、WAU、MAU 和 DAU/MAU。
  - 定义渗透率、D1、D7、D30 和 Cohort。
  - 定义时区、自然日和统计周期。
- 验收：
  - 每个指标具有分子、分母、去重键、时间窗口和排除条件。

#### IR02-DR-FND-005 IR-01 关联合同

- 优先级：P0
- 对应：SR-FBK-003、SR-FBK-006
- 工作内容：
  - 冻结 `message_id`、`request_id`、`trace_id` 和可选 `span_id` 关联。
  - 定义 Trace 过期后的反馈展示。
  - 定义 Feedback 跳转 Trace 的权限行为。
- 验收：
  - Feedback 关联不会依赖可变的前端状态或消息序号。

### 7.2 阶段 B：用户反馈提交

#### IR02-DR-FBK-001 Feedback 数据模型

- 优先级：P1
- 对应：SR-FBK-001～004
- 工作内容：
  - 保存评价类型、原因、说明和创建更新时间。
  - 关联用户、租户、会话、Assistant Message、请求、Agent、版本和 Trace。
  - 保留必要的关联快照。
- 验收：
  - 每条 Feedback 都绑定一个具体 Assistant Message。

#### IR02-DR-FBK-002 重复反馈控制

- 优先级：P1
- 对应：SR-FBK-004
- 工作内容：
  - 以“身份主体 + Assistant Message”建立有效 Feedback 唯一规则。
  - 重复操作更新原评价。
  - 定义评价从点赞改为点踩或取消时的历史记录。
- 验收：
  - 重复点击不会产生重复统计。

#### IR02-DR-FBK-003 Feedback API

- 优先级：P1
- 对应：SR-FBK-001～004
- 工作内容：
  - 创建或更新 Feedback。
  - 查询当前用户对指定消息的 Feedback。
  - 取消 Feedback。
  - 校验消息归属和可反馈状态。
- 验收：
  - Feedback 提交成功率达到目标。
  - 用户不能评价其他用户不可访问的消息。

#### IR02-DR-FBK-004 Chat 反馈入口

- 优先级：P1
- 对应：SR-FBK-001、SR-FBK-002
- 工作内容：
  - 在 Assistant Message 展示点赞点踩。
  - 点踩后展示原因和补充说明。
  - 展示当前评价并允许修改。
  - 提交失败时提供明确反馈。
- 验收：
  - 用户可以在当前对话内完成提交和修改。

#### IR02-DR-FBK-005 反馈内容安全

- 优先级：P0
- 对应：SR-SEC-004
- 工作内容：
  - 限制文字长度和格式。
  - 防止脚本和恶意输入。
  - 对反馈内容和身份信息实施脱敏。
  - 定义完整反馈内容的查看权限。
- 验收：
  - Feedback 页面不会执行用户输入脚本。
  - 敏感内容不进入未授权查询结果。

### 7.3 阶段 C：反馈管理和回溯

#### IR02-DR-FBK-006 Feedback 查询

- 优先级：P1
- 对应：SR-FBK-005
- 工作内容：
  - 支持 Agent、版本、原因、状态、负责人、租户和时间筛选。
  - 支持分页和排序。
- 验收：
  - Agent 负责人只能查看有权负责的 Agent Feedback。

#### IR02-DR-FBK-007 Feedback Case

- 优先级：P1
- 对应：SR-FBK-007
- 工作内容：
  - 为负面反馈建立处理记录。
  - 支持状态、负责人、处理结论和关闭。
  - 记录操作历史。
- 验收：
  - Feedback 的每次状态和负责人变化都可审计。

#### IR02-DR-FBK-008 对话和调用链回溯

- 优先级：P1
- 对应：SR-FBK-006
- 工作内容：
  - 从 Feedback 跳转原对话和具体 Assistant Message。
  - 从 Feedback 跳转 IR-01 Trace。
  - 如果有问题 Span，自动定位节点。
  - Trace 过期时显示明确提示。
- 验收：
  - 负面反馈能够完成“Feedback → Message → Trace/Span”回溯。

#### IR02-DR-UI-001 Feedback 管理页面

- 优先级：P1
- 对应：SR-FBK-005～007
- 工作内容：
  - Feedback 列表和筛选。
  - Feedback 详情。
  - Feedback Case 处理。
  - 对话和 Trace 回溯入口。
- 验收：
  - 负责人可以在一个处理流程中完成查看、诊断、记录结论和关闭。

### 7.4 阶段 D：反馈分析

#### IR02-DR-MET-001 Feedback 聚合

- 优先级：P1
- 对应：SR-FBK-008
- 指标：
  - 可反馈回答数
  - 有效 Feedback 数
  - 反馈率
  - 点赞率一：点赞数/有效 Feedback 数
  - 点赞率二：点赞数/可反馈回答数
  - 点踩率
  - 原因分布
- 验收：
  - 页面明确标注使用的点赞率口径。
  - 修改 Feedback 后聚合结果不重复计数。

#### IR02-DR-MET-002 Feedback 多维分析

- 优先级：P2
- 对应：SR-FBK-008、SR-OPS-007
- 工作内容：
  - 按 Agent、版本、租户、原因和时间分析。
  - 与 IR-01 的耗时、错误和调用节点关联。
- 验收：
  - 可以识别响应慢、工具结果错误和回答错误等主要反馈来源。

#### IR02-DR-UI-002 Feedback 分析页面

- 优先级：P2
- 工作内容：
  - 反馈趋势
  - 点赞点踩
  - 原因分布
  - Agent 和版本对比
- 验收：
  - 页面指标来自统一聚合服务。

### 7.5 阶段 E：用户事件和基础运营分析

#### IR02-DR-OPS-001 User Event

- 优先级：P1
- 对应：SR-OPS-001
- 工作内容：
  - 生成不可变的有效用户请求事件。
  - 保存用户、租户、Agent、版本、请求、状态和时间。
  - 支持幂等和去重。
- 验收：
  - 相同请求重放或重复消费不会重复计数。

#### IR02-DR-OPS-002 活跃用户

- 优先级：P1
- 对应：SR-OPS-002
- 工作内容：
  - 计算 DAU、WAU、MAU 和 DAU/MAU。
  - 支持租户、Agent、部门和用户类型筛选。
- 验收：
  - 活跃用户只由有效行为产生，不使用页面访问作为活跃。

#### IR02-DR-OPS-003 请求量和人均请求

- 优先级：P1
- 对应：SR-OPS-003
- 工作内容：
  - 计算请求总数、成功请求、失败请求和人均请求。
  - 支持 Agent、租户和时间筛选。
- 验收：
  - 请求状态与 IR-01/Chat 使用统一口径。

#### IR02-DR-OPS-004 用户渗透率

- 优先级：P1
- 对应：SR-OPS-004
- 工作内容：
  - 计算平台和 Agent 级权限用户数。
  - 计算实际使用用户数。
  - 计算周期渗透率。
- 验收：
  - 缺少分母时不展示误导性的百分比。

### 7.6 阶段 F：留存和 Cohort

#### IR02-DR-OPS-005 新用户和首次使用

- 优先级：P1
- 对应：SR-OPS-005、SR-OPS-008
- 工作内容：
  - 定义平台首次使用和 Agent 首次使用。
  - 处理历史数据补算和身份合并。
- 验收：
  - 每个新用户具有可追溯的首次有效行为。

#### IR02-DR-OPS-006 D1/D7/D30 留存

- 优先级：P2
- 对应：SR-OPS-005
- 工作内容：
  - 按冻结口径计算 D1、D7 和 D30。
  - 支持平台和 Agent 维度。
- 验收：
  - 首次使用、观察窗口和回访行为均可解释。

#### IR02-DR-OPS-007 Cohort 分析

- 优先级：P2
- 对应：SR-OPS-006
- 工作内容：
  - 周 Cohort 和月 Cohort。
  - 支持租户、Agent、部门和用户类型。
- 验收：
  - Cohort 分母固定，后续周期只更新回访结果。

#### IR02-DR-UI-003 运营分析页面

- 优先级：P2
- 对应：SR-OPS-002～007
- 工作内容：
  - 活跃趋势
  - 请求量和人均请求
  - 平台及 Agent 渗透
  - D1/D7/D30
  - 周/月 Cohort
  - 反馈与行为关联
- 验收：
  - 页面筛选和指标使用统一数据服务和口径版本。

### 7.7 阶段 G：数据权限和治理

#### IR02-DR-SEC-001 Feedback 和运营数据权限

- 优先级：P0
- 对应：SR-SEC-003
- 工作内容：
  - 普通用户只能访问自己的 Feedback。
  - Agent 负责人访问其负责 Agent。
  - 租户管理员访问本租户。
  - 平台管理员权限单独授予和审计。
- 验收：
  - 用户、Agent 和租户边界均有自动化权限测试。

#### IR02-DR-SEC-002 用户删除和账号合并

- 优先级：P1
- 对应：IR-02 边界约束
- 工作内容：
  - 定义用户删除后 Feedback 和聚合保留规则。
  - 定义账号合并后的去重和首次使用规则。
  - 定义匿名身份转登录身份的处理。
- 验收：
  - 删除和合并操作不会造成指标重复或越权暴露。

#### IR02-DR-SEC-003 数据保留和过期提示

- 优先级：P1
- 工作内容：
  - 定义 Feedback、Case、User Event 和聚合保留周期。
  - 处理 Feedback 与 Trace 保留周期不一致。
- 验收：
  - Trace 已过期时 Feedback 页面明确提示，不返回错误跳转。

#### IR02-DR-SEC-004 指标口径版本

- 优先级：P1
- 对应：SR-OPS-008
- 工作内容：
  - 保存指标定义版本。
  - 页面和接口返回口径版本、时区和观察窗口。
- 验收：
  - 同名指标在不同页面和导出结果中一致。

## 14. 验收标准

### 14.1 用户反馈最小闭环

1. 用户对具体 Assistant Message 点赞或点踩。
2. 点踩可以选择原因和填写说明。
3. Feedback 自动关联用户、租户、会话、请求、Agent 和 Trace。
4. 同一用户同一回答重复操作更新原 Feedback。
5. Agent 负责人可以查询 Feedback。
6. 负面 Feedback 可以建立 Case、分配负责人和记录结论。
7. 用户可以从 Feedback 回溯对话和 IR-01 调用链。

### 14.2 运营分析最小闭环

1. 平台产生稳定的有效用户请求事件。
2. 可以统计 DAU、MAU、请求总数和人均请求数。
3. 可以根据权限用户分母计算 Agent 渗透率。
4. 可以计算约定口径的 D1、D7、D30。
5. 可以按 Agent、租户和时间筛选。

### 14.3 量化验收

| 指标 | 首期目标 |
| --- | --- |
| Feedback 关联完整率 | 不低于 95% 可关联 request_id 和 trace_id |
| Feedback 提交成功率 | 不低于 99% |
| 重复 Feedback 控制 | 同一身份同一回答一个有效评价 |
| 负面 Feedback 回溯率 | 不低于 90% 可回溯调用链 |
| 活跃指标数据完整率 | 不低于 99% |
| User Event 采集成功率 | 不低于 99% |
| 运营指标时效 | 不超过约定周期 |
| 指标口径一致性 | 页面、接口和导出一致 |
| 用户身份识别率 | 达到业务约定目标 |

## 15. 编码前待确认事项

1. Feedback 是否只允许评价最终 Assistant Message。
2. Assistant Message 删除后 Feedback 是否保留。
3. Feedback 是否允许取消。
4. 点赞是否也允许选择原因和填写文字。
5. 点踩原因字典和多选/单选规则。
6. Feedback Case 是否仅为负面反馈自动创建。
7. Case 状态、负责人来源和关闭权限。
8. Agent 是否等同于 AINA。
9. 一次请求使用多个 AINA 时如何归属使用用户和 Feedback。
10. 用户和租户身份由哪个认证系统提供。
11. 匿名用户使用 Cookie、设备 ID、会话 ID 还是其他标识。
12. 部门和用户类型来自哪个系统。
13. 平台和 Agent 权限用户清单来自哪个系统。
14. 权限在周期内变化时，渗透率分母采用期初、期末还是周期并集。
15. 有效请求是否包含失败、取消、审批中、定时和 Debug 请求。
16. 平台首次使用和 Agent 首次使用是否分别计算。
17. 留存采用自然日、滚动还是区间口径。
18. 统计时区使用租户时区还是统一平台时区。
19. 用户删除、账号合并和匿名转登录如何处理历史数据。
20. Feedback、User Event、Case 和运营聚合分别保留多久。
21. Trace 过期后 Feedback 页面展示哪些技术信息。
22. 是否需要运营数据导出；如需要，导出权限和脱敏规则是什么。

## 16. 最终结论

IR-02 的反馈闭环和运营分析应作为两个子域分阶段建设。

当前项目可以复用 Message ID、Conversation ID、Trace ID、用户、租户、AINA 和请求状态等基础数据，但必须先解决：

1. 可信用户身份和匿名用户识别。
2. Agent 归属和权限用户分母。
3. Feedback 与 Message、Request、Trace 的稳定关联合同。
4. 有效请求、活跃、渗透和留存的统一指标口径。

Feedback 提交和处理可以较早形成业务价值；渗透率、留存和 Cohort 则不能在身份、权限用户和观察窗口未明确时提前实现。

IR-02 最终应与 IR-01 形成完整闭环：

用户请求 → IR-01 记录运行过程 → 用户提交 Feedback → IR-02 记录体验并形成 Case → 负责人回溯 IR-01 Trace/Span → 优化 Agent、模型或工具 → 通过反馈和运营指标验证效果。
