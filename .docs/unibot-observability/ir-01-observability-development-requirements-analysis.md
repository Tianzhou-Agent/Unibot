# IR-01 平台运行可观测与质量分析——开发需求分析

## 1. 文档说明

### 1.1 文档目的

本文档针对原始需求中的“IR-01 平台运行可观测与质量分析”，结合 Unibot 当前实现，形成可独立评审和开发的需求分析。

本文档回答：

1. 当前项目已经具备哪些可观测能力。
2. 当前实现与 IR-01 各项 SR 的差距。
3. 本期需要建设哪些后端、前端、数据和安全能力。
4. 各开发阶段的依赖和验收标准。
5. 编码前必须确认哪些产品和技术决策。

本文档不包含数据库 DDL、完整 API Schema、详细技术设计和工期估算。

### 1.2 需求范围

本需求覆盖：

- 用户请求级 Trace 生成与透传
- Agent、模型、工具、AINA 和内部 Span
- 父子、嵌套、并行和重试关系
- 调用链检索和详情展示
- 错误中心和错误节点定位
- 原始日志关联
- Agent、模型和工具性能分析
- 平均值、P50、P95 和 P99
- Agent、版本、模型、工具、租户和时间筛选
- 数据权限和敏感信息保护

### 1.3 非本期范围

- 基于大模型的自动根因分析
- 自动修复 Agent 配置或代码
- 完整告警平台
- 模型回答内容质量自动评测
- Agent A/B 实验平台
- 成本预算和配额控制
- 跨企业、跨平台的全链路追踪
- IR-02 中的用户反馈和运营增长页面

### 1.4 优先级

| 优先级 | 定义 |
| --- | --- |
| P0 | 安全、数据模型或架构阻塞项 |
| P1 | IR-01 最小诊断和分析闭环必须具备 |
| P2 | 本期体验增强和高级分析 |
| P3 | 后续优化 |

## 2. 业务目标和使用场景

### 2.1 业务目标

IR-01 需要让平台能够回答：

- 一次请求经过了哪些 Agent、模型、工具和内部处理节点。
- 请求失败发生在哪个节点。
- 错误属于模型、工具、Agent 编排还是平台服务。
- 每个节点消耗了多少时间和 Token。
- 哪个 Agent、版本、模型或工具的性能和稳定性较差。
- Agent 或模型配置变更后，性能和成功率发生了什么变化。

### 2.2 核心场景

#### 场景一：线上错误排查

用户从错误中心进入 Trace，平台自动定位异常 Span，并展示错误信息、脱敏输入输出和关联日志。

#### 场景二：性能瓶颈分析

平台负责人查看 Agent 总耗时和每个调用节点耗时，识别模型、工具或平台内部瓶颈。

#### 场景三：模型体验评估

模型负责人比较 TTFT、总耗时、Token、输出速度和成功率。

#### 场景四：工具质量治理

工具负责人查看调用次数、成功率、错误率、超时率、重试次数和耗时。

#### 场景五：版本变更验证

Agent 负责人比较不同 Agent/AINA 或配置版本的成功率、耗时、Token 和错误分布。

## 3. 当前项目能力分析

### 3.1 Trace 数据模型

当前项目已有 `TraceRecord` 和 `TraceEvent`。

`TraceRecord` 已包含：

- `trace_id`
- `conversation_id`
- `user_id`
- `tenant_id`
- Trace 状态
- 创建和完成时间
- Trace Event 列表

可以复用：

- Trace 与会话、用户和租户的关联。
- Trace 状态和时间信息。
- 现有 Trace 查询和测试入口。

主要问题：

- `TraceEvent` 是平铺事件，不是 Span。
- 没有 `span_id` 和 `parent_span_id`。
- 开始和完成事件没有统一的 Span 生命周期。
- 无法稳定表达嵌套、并行和重试关系。

### 3.2 Agent 执行采集

当前 Agent Runtime 会在一次 Chat 中记录：

- 用户请求
- 能力发现
- 模型请求、完成和失败
- Tool、AINA 和内建能力请求、完成和失败
- 审批暂停、恢复、拒绝和取消
- 最终响应

可以复用：

- 现有事件种类可以映射为 Agent、Model、Tool、AINA 和 Internal Span。
- 已有 `call_id` 可以辅助逻辑调用关联。
- 已有迭代次数和 Token 汇总。

主要问题：

- Trace 创建和事件写入位于 Agent 主链路。
- Trace 存储失败会让 Chat 失败，不符合“采集失败不得阻塞业务”的约束。
- 根 Agent 节点没有独立 Span。
- 审批暂停和恢复时的持续时间和状态语义需要统一。

### 3.3 模型调用采集

当前 `LLMCallRecord` 已记录：

- `call_id`
- `trace_id`
- 上下文类型和 ID
- Endpoint 和 Model
- 请求和响应
- 状态、错误和总耗时
- 输入、输出和总 Token

可以复用：

- Model Span 的基础数据来源。
- 模型调用详情页。
- Token 和总耗时统计逻辑。

主要问题：

- 流式调用没有记录首个有效 Token 时间。
- 没有缓存 Token 和推理 Token 的统一字段。
- 没有稳定关联 Model Span 的 `span_id`。
- Provider、模型配置版本和 Agent 版本没有完整快照。
- 输出速度当前基于总耗时估算，不能准确区分等待和生成阶段。
- LLM 请求和响应没有统一经过 Trace 脱敏流程。

### 3.4 Tool 和 AINA 调用采集

当前已经记录：

- 能力类型和能力 ID
- `call_id`
- 函数名
- 输入参数和输出结果
- 耗时
- 错误码、错误来源和是否可重试

项目已经存在 Tool `version`、AINA Manifest `version` 和安装版本。

可以复用：

- Tool/AINA Span 的输入、输出和耗时。
- 工具和 AINA 版本分析维度。
- 现有超时、重试和错误处理。

主要问题：

- Gateway 内部重试没有逐次记录 Attempt。
- 逻辑调用次数和实际请求次数无法区分。
- 当前工具调用主要顺序执行，没有并行关系数据。
- Trace Event 没有稳定保存工具和 AINA 版本快照。
- AINA 是 Agent 维度还是工具维度尚未统一。

### 3.5 错误能力

当前 `PlatformError` 已包含：

- 错误码
- 错误信息
- HTTP 状态码
- 是否可重试
- 错误来源
- 用户提示
- Debug 信息

可以复用：

- Error Event 的错误码、来源和重试属性。
- API、模型、工具和存储错误映射。

主要问题：

- HTTP `request_*` 标识与 Agent `trace_*` 标识相互独立。
- 没有独立 Error Event 存储。
- 没有错误指纹、错误趋势和错误分布。
- 不能从错误记录稳定定位唯一 Span。

### 3.6 日志能力

当前项目使用 Python 标准日志，部分异常日志通过 `extra` 附加 `trace_id`。

主要问题：

- 没有统一 Trace/Span 日志上下文。
- 普通日志不能保证附带 Trace ID。
- 没有结构化日志规范。
- 没有日志后端查询接口。
- 没有从 Span 查看关联日志的能力。

### 3.7 存储能力

当前 MySQL 业务记录使用通用结构：

- `id`
- `payload` JSON
- `updated_at`

当前 Trace 作为一个完整 JSON 保存；增加事件时会更新整个 Trace。服务启动时还会加载全部 Trace 和 LLM Call 到内存。

可以复用：

- MySQL 和 Redis 基础设施。
- Repository 抽象。
- NAS/S3 方向的大字段存储能力。

主要问题：

- 无法高效按 Agent、模型、工具、状态和时间索引。
- Trace 越长，JSON 更新放大越明显。
- 全量内存加载不适合长期保留。
- 不适合分位数、多维趋势和错误聚合。
- 没有热冷数据、归档和删除策略。

### 3.8 前端能力

当前 Debug 页面已支持：

- Trace 列表和会话分组
- Trace 状态
- 事件时间线
- 模型调用列表和详情
- 请求、响应、耗时和 Token 展示
- 从 Chat 运行结果跳转 Trace

可以复用：

- Debug 页面整体布局。
- Trace 列表、详情和模型调用组件。
- Chat 到 Trace 的跳转入口。

主要问题：

- 当前 Trace 列表没有服务端分页和完整筛选。
- 调用关系是事件列表，不是调用树或瀑布图。
- 没有错误中心和关联日志面板。
- 没有 Agent、模型和工具分析页面。
- 前端固定使用 `anonymous/default`。

### 3.9 权限和敏感信息

当前已有：

- `RequestActor` 模型
- Conversation、Trace 等对象中的用户和租户字段
- Trace Payload 脱敏和截断工具

主要问题：

- Chat 的用户和租户仍可以由客户端请求参数提供。
- Trace 详情接口没有完整的资源权限校验。
- LLM Call 列表是全局查询。
- LLM Call 原始请求和响应没有统一脱敏。
- 没有字段级内容查看权限。

## 4. 总体结论

当前能力可以作为 IR-01 的开发起点，但不能直接作为生产实现继续堆叠。

必须先完成四项底层改造：

1. 将平铺 Trace Event 升级为正式 Trace/Span 模型。
2. 将可观测写入与 Agent 主链路解耦。
3. 将通用 JSON 存储升级为可索引、可分页、可聚合的明细和分析存储。
4. 建立可信身份、租户隔离和统一敏感数据策略。

在上述基础完成前，不建议先开发完整分析页面，因为页面指标将缺少可靠数据来源和统一口径。

## 6. 开发需求拆分

### 6.1 阶段 A：口径、身份和架构决策

#### IR01-DR-FND-001 统一标识体系

- 优先级：P0
- 工作内容：
  - 定义 `request_id`、`trace_id`、`span_id`、`logical_call_id` 和 `attempt_id`。
  - 明确 HTTP 请求和 Agent Trace 的关系。
  - 明确外部 Trace Header 的信任规则。
- 验收：
  - 标识定义、生成方、透传方和查询权限形成统一文档。

#### IR01-DR-FND-002 统一指标字典

- 优先级：P0
- 工作内容：
  - 定义有效请求、成功、失败、超时、取消和审批中。
  - 定义 Agent 耗时、TTFT、模型总耗时和工具耗时。
  - 定义 Token、输出速度、调用次数和重试次数。
  - 定义平均值和分位数时间窗口。
- 验收：
  - 每个指标都有分子、分母、去重键、时间窗口和排除条件。

#### IR01-DR-FND-003 Agent 和版本口径

- 优先级：P0
- 工作内容：
  - 明确 Unibot 主 Agent 与 AINA 的统计关系。
  - 定义 Agent、AINA、模型配置和 Tool 的版本快照。
- 验收：
  - 历史 Trace 的版本维度不会随当前配置变化。

#### IR01-DR-FND-004 存储、日志和容量方案

- 优先级：P0
- 工作内容：
  - 选择 Trace/Span 明细存储。
  - 选择指标聚合存储。
  - 确定日志查询来源。
  - 确定大 Payload、保留周期、采样和归档策略。
  - 评估是否使用 OpenTelemetry 标准。
- 验收：
  - 方案能够支撑 1 分钟明细、5 分钟聚合和 3 秒常规查询目标。
  - 方案不依赖全量内存加载。

#### IR01-DR-FND-005 可信身份和权限模型

- 优先级：P0
- 工作内容：
  - 通过可信中间件注入用户和租户。
  - 定义普通用户、Agent 负责人、租户管理员和平台管理员权限。
  - 定义 Trace、Span、日志和 Payload 的访问边界。
- 验收：
  - 修改请求参数不能访问其他主体数据。

### 6.2 阶段 B：Trace/Span 采集底座

#### IR01-DR-OBS-001 Trace 上下文生成与透传

- 优先级：P0
- 对应：SR-OBS-001
- 工作内容：
  - 在用户请求入口创建或接收合法 Trace 上下文。
  - 透传到 Chat、Agent、AINA、Tool、模型、异步任务和日志。
  - 保持向现有 AINA 协议的兼容。
- 验收：
  - 一次用户请求的所有节点可通过统一 Trace 标识关联。

#### IR01-DR-OBS-002 Span 生命周期

- 优先级：P0
- 对应：SR-OBS-002、SR-OBS-003
- 工作内容：
  - 建立 Span 开始、完成、失败和取消状态。
  - 建立父子、嵌套和并行关系。
  - 建立逻辑调用与 Attempt 关系。
  - 保证结束和补写幂等。
- 验收：
  - 正常、异常、中断和恢复执行均能形成结构正确的调用树。

#### IR01-DR-OBS-003 Agent Span

- 优先级：P1
- 对应：SR-PERF-001
- 工作内容：
  - 创建根 Agent Span。
  - 记录 Agent/AINA、版本、迭代数、步骤数和最终状态。
  - 正确表达审批暂停和恢复。
- 验收：
  - Agent 单轮耗时符合原始指标定义。

#### IR01-DR-OBS-004 Model Span

- 优先级：P1
- 对应：SR-PERF-002
- 工作内容：
  - 将 LLM Call 与唯一 Model Span 关联。
  - 记录 Provider、模型、配置版本、流式状态和完成原因。
  - 记录 TTFT、总耗时和各类 Token。
- 验收：
  - 流式模型调用能够查询首 Token 和结束时间。

#### IR01-DR-OBS-005 Tool 和 AINA Span

- 优先级：P1
- 对应：SR-PERF-003
- 工作内容：
  - 采集 Tool、AINA 和内建能力 Span。
  - 记录工具版本、输入输出、状态和耗时。
  - 将每次 Gateway 重试记录为 Attempt。
- 验收：
  - 可以区分逻辑调用次数、实际调用次数和重试次数。

#### IR01-DR-OBS-006 采集降级

- 优先级：P0
- 工作内容：
  - 将 Trace/Span 写入与 Agent 结果解耦。
  - 定义缓冲、批量、重试、积压和丢弃策略。
  - 记录采集覆盖率和失败率。
- 验收：
  - 可观测存储故障时，Chat 业务仍能完成。
  - 数据丢失或延迟可被发现。

#### IR01-DR-OBS-007 Payload 安全处理

- 优先级：P0
- 对应：SR-SEC-002
- 工作内容：
  - Trace Event、LLM Call、Tool、日志统一脱敏。
  - 支持摘要、截断和外部 Payload 引用。
  - 实施字段级内容查看权限。
- 验收：
  - 密钥、Token、Cookie 和认证信息不进入查询结果。

### 6.3 阶段 C：检索、错误和日志

#### IR01-DR-QRY-001 Trace 检索

- 优先级：P1
- 对应：SR-OBS-004
- 工作内容：
  - 支持 Trace ID、用户、Agent、版本、模型、工具、状态、租户和时间筛选。
  - 支持分页、排序和摘要返回。
- 验收：
  - 常规查询在目标数据规模下 3 秒内返回。

#### IR01-DR-QRY-002 Trace/Span 详情

- 优先级：P1
- 对应：SR-OBS-005
- 工作内容：
  - 返回调用树、状态、耗时、版本、Token、Payload 摘要和错误。
  - 支持 `trace_id + span_id` 精确定位。
- 验收：
  - 给定 Trace 和 Span 标识可稳定返回唯一节点。

#### IR01-DR-ERR-001 标准 Error Event

- 优先级：P1
- 对应：SR-ERR-001
- 工作内容：
  - 定义错误 ID、错误码、类型、来源、指纹、严重程度和重试属性。
  - 统一映射 API、模型、Tool、AINA、平台和存储错误。
- 验收：
  - 执行错误能够关联 Trace 和异常 Span。

#### IR01-DR-ERR-002 错误中心

- 优先级：P1
- 对应：SR-ERR-002、SR-ERR-003
- 工作内容：
  - 错误趋势、分布、明细和筛选。
  - 从 Error 跳转 Trace 并选中异常 Span。
- 验收：
  - 模型或工具失败可以通过错误中心完成回溯。

#### IR01-DR-LOG-001 日志上下文和查询

- 优先级：P1
- 对应：SR-LOG-001
- 工作内容：
  - 注入 Trace/Span 日志上下文。
  - 统一结构化日志字段和脱敏。
  - 对接日志存储并提供关联日志接口。
- 验收：
  - 异常 Span 可以查看同节点、同时间范围的关联日志。

#### IR01-DR-UI-001 调用链运行中心

- 优先级：P1
- 对应：SR-OBS-004、SR-OBS-005
- 工作内容：
  - 在现有 Debug 页面基础上增加服务端检索和分页。
  - 增加调用树或瀑布图。
  - 增加 Span 详情、异常定位和日志面板。
- 验收：
  - 用户无需手工复制多个 ID 即可完成错误定位。

### 6.4 阶段 D：性能和质量分析

#### IR01-DR-MET-001 聚合指标服务

- 优先级：P1
- 对应：SR-PERF-004、SR-PERF-005
- 工作内容：
  - 从 Trace/Span 明细生成时间窗口聚合。
  - 统一平均值、P50、P95 和 P99。
  - 支持迟到数据、重复数据和补算。
- 验收：
  - 聚合延迟不超过约定的 5 分钟。

#### IR01-DR-MET-002 Agent 分析

- 优先级：P1
- 对应：SR-PERF-001
- 指标：
  - 请求数
  - 成功率和错误率
  - 平均、P50、P95、P99 耗时
  - 步骤数、模型调用数、工具调用数和重试数
- 验收：
  - 支持 Agent、版本、租户和时间分析。

#### IR01-DR-MET-003 模型分析

- 优先级：P1
- 对应：SR-PERF-002
- 指标：
  - 调用次数和成功率
  - TTFT 和总耗时
  - 输入、输出、缓存、推理和总 Token
  - 输出速度
- 验收：
  - 支持 Provider、模型、Agent、版本和时间对比。

#### IR01-DR-MET-004 工具分析

- 优先级：P1
- 对应：SR-PERF-003
- 指标：
  - 逻辑调用和实际 Attempt 数
  - 成功率、错误率和超时率
  - 平均、P50、P95、P99 耗时
  - 重试次数
- 验收：
  - 能识别高错误、高超时和高延迟工具。

#### IR01-DR-UI-002 性能分析页面

- 优先级：P2
- 对应：SR-PERF-001～005
- 工作内容：
  - Agent 分析页
  - 模型分析页
  - 工具分析页
  - 多维筛选和版本对比
- 验收：
  - 页面指标全部来自统一指标服务。

## 7. 概念数据对象

以下对象用于指导详细设计，不代表最终数据库表：

| 对象 | 主要职责 |
| --- | --- |
| Trace | 一次端到端请求的摘要、根状态和关联主体 |
| Span | 一次 Agent、Model、Tool、AINA 或内部处理活动 |
| Span Link | 并行、异步或跨上下文关联 |

## 10. 非功能要求

### 10.1 性能

- 明细在请求完成后 1 分钟内可查询。
- 聚合延迟不超过约定的 5 分钟。
- 常规检索 3 秒内返回。
- 所有列表采用服务端分页。
- 不允许前端加载全部明细后计算平台指标。

### 10.2 可用性

- 采集故障不阻塞 Agent。
- 查询和分析故障不影响 Chat。
- 聚合失败可以重试和补算。
- Span 写入和结束操作应幂等。

### 10.3 安全

- 敏感信息在进入可观测存储前处理。
- 完整 Prompt、响应和日志需要额外权限。
- 用户和租户不能由普通客户端自由指定。
- 管理员查询需要审计。

## 13. 验收标准

### 13.1 最小业务闭环

1. 用户发起 Agent 请求。
2. 系统生成完整 Trace 和根 Agent Span。
3. 模型、Tool 和 AINA 调用形成子 Span。
4. 模型或工具失败时生成 Error Event。
5. 错误中心可以查询该错误。
6. 用户进入 Trace 后自动定位异常 Span。
7. 用户可以查看脱敏输入输出、错误和关联日志。
8. 分析页面可以查看 Agent、模型和工具的耗时、成功率和 Token。

### 13.2 量化验收

| 指标 | 首期目标 |
| --- | --- |
| Trace 覆盖率 | 不低于 95% 的有效用户请求生成完整 Trace |
| 错误关联率 | 不低于 90% 的执行错误关联 Trace 和 Span |
| 错误节点定位率 | 不低于 90% |
| 日志关联率 | 不低于 90% 的异常 Span 可查看关联日志 |
| 核心字段完整率 | TTFT、耗时、Token 等不低于 95% |
| 明细查询时效 | 请求完成后 1 分钟内 |
| 聚合时效 | 不超过约定的 5 分钟 |
| 常规查询 | 3 秒内返回 |

具体数值需要结合流量和存储方案复核。

## 14. 编码前待确认事项

1. Agent 是否等同于 AINA，还是包含 Unibot 主 Agent。
2. `request_id` 是否直接使用用户 Message ID。
3. HTTP Trace 与 Agent Trace 是合并还是父子关系。
4. 有效请求是否包含失败、取消、审批中、定时任务和 Debug 请求。
5. Agent、AINA、Tool 和模型配置分别采用什么版本口径。
6. 是否已经有企业 Trace、指标和日志平台可复用。
7. Prompt、模型响应和 Tool 结果是否允许全文保存。
8. 哪些角色可以查看完整输入输出。
9. Trace、日志、Payload 和聚合指标分别保留多久。
10. 预计日请求量、峰值 QPS、平均 Span 数和平均 Payload 大小。
11. 是否允许采样；错误 Trace 是否必须全量保留。
12. 审批暂停跨较长时间时，Agent 耗时如何统计和展示。

## 15. 最终结论

IR-01 的首要工作是把现有 Debug Trace 升级为正式的生产可观测数据体系，而不是先增加更多前端统计。

现有 Trace、LLM Call、Tool/AINA 事件、错误模型、脱敏工具和 Debug 页面均可复用，但需要在以下方面完成结构性改造：

1. Trace Event 升级为 Trace/Span。
2. 采集写入与 Agent 主链路解耦。
3. 可观测明细与业务通用 JSON 存储解耦。
4. 统一身份、权限和敏感数据处理。
5. 在可靠明细基础上统一计算性能和质量指标。

完成这些改造后，IR-01 才能为错误诊断、性能治理、版本对比以及 IR-02 的反馈回溯提供稳定底座。
