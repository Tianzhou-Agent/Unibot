# Unibot 可观测、质量与运营能力开发需求分析

## 1. 文档说明

### 1.1 文档目的

本文档基于《IR-01 平台运行可观测与质量分析》和《IR-02 用户体验反馈与运营增长分析》，结合 Unibot 当前代码、数据模型、接口、存储和前端实现，形成面向当前项目的开发需求分析。

本文档重点回答：

1. 原始需求中哪些能力已经存在、哪些可以复用。
2. 当前实现与目标之间有哪些差距。
3. 应拆分出哪些开发任务，以及任务之间的依赖关系。
4. 每个阶段应如何验收。
5. 哪些产品、数据和架构口径必须在编码前确认。

本文档不包含详细技术设计、数据库 DDL、接口字段定义、代码实现和工期承诺。

### 1.2 分析依据

- 原始需求：`requirements.md`
- 后端：FastAPI、LangGraph/LangChain、MySQL、Redis、NAS
- 前端：React、TypeScript、Vite
- 当前 Trace、模型调用、错误和脱敏实现
- 当前会话、消息、AINA、工具和用户租户模型
- 当前后端测试和前端 E2E 测试

### 1.3 优先级定义

| 优先级 | 定义 |
| --- | --- |
| P0 | 安全、数据口径或底层架构阻塞项，未完成前不应进入上层功能开发 |
| P1 | 本期最小业务闭环必须具备 |
| P2 | 本期分析、运营和体验增强能力 |
| P3 | 后续优化项，不影响首期闭环 |

## 2. 执行摘要

Unibot 当前已经具备一套面向开发调试的 Trace MVP：

- 每次 Chat 请求会生成 Agent Trace。
- Trace 已关联会话、用户和租户。
- Agent 执行过程中会记录模型、工具、AINA 和内部处理事件。
- 模型调用已经单独记录请求、响应、耗时和基础 Token。
- Trace 事件中的部分输入输出已经支持脱敏和截断。
- 前端已有 Debug 页面，可查看 Trace、事件和模型调用详情。
- Chat 响应和 Assistant Message 已具备支持反馈关联的 `trace_id` 和 `message_id`。

但当前能力仍属于“调试事件记录”，不能直接满足原始需求中的生产级可观测和运营分析：

1. 当前 `TraceEvent` 是平铺事件，不是具有父子关系的 Span。
2. Trace、Span、Error 和 Log 之间没有统一的节点级关联。
3. Trace 以整段 JSON 保存并整体加载到内存，难以支撑分页检索、分位数统计和大规模数据保留。
4. Trace 创建和事件落库位于业务主链路，采集故障会影响 Chat。
5. 流式模型调用没有记录 TTFT。
6. 工具内部重试没有形成独立 Attempt 数据。
7. 没有错误中心、日志查询和后端聚合分析服务。
8. 用户和租户身份目前仍主要由请求参数提供，Trace 和 LLM 明细接口权限隔离不足。
9. LLM Call 保存的完整请求和响应未统一经过 Trace 脱敏流程。
10. IR-02 的 Feedback、用户事件、活跃度、渗透率、留存和 Cohort 能力尚未建设。

因此，本需求应按以下顺序实施：

1. 数据口径、身份权限和存储方案定稿。
2. 将现有 Trace Event 升级为可关联的 Trace/Span 数据体系。
3. 建设调用链检索、错误中心、日志关联和诊断页面。
4. 建设 Agent、模型和工具性能分析。
5. 建设用户反馈闭环。
6. 在用户身份和权限用户来源稳定后建设运营增长分析。

## 3. 当前项目相关能力分析

### 3.1 当前 Trace 能力

当前 `TraceRecord` 包含：

- `trace_id`
- `conversation_id`
- `user_id`
- `tenant_id`
- Trace 状态
- Trace 事件列表
- 创建和完成时间

Agent Runtime 在收到 Chat 请求后创建新的 `trace_id`，并记录：

- `user.request`
- 模型请求和完成
- 工具、AINA 或内建能力请求和完成
- 能力发现和路由信息
- 审批相关事件
- 最终响应

可复用价值：

- 已经形成 User Request 到 Agent 执行过程的基本关联。
- 现有事件种类可以作为 Span 类型和 Span 属性设计的输入。
- 现有 Trace 测试可以作为升级后的回归测试基础。

当前限制：

- 没有 `span_id` 和 `parent_span_id`。
- 开始事件和完成事件是独立记录，没有统一 Span 生命周期。
- 模型 Trace Event 与 `LLMCallRecord` 没有明确的节点 ID 关联。
- 不能稳定表达嵌套 Agent、并行调用和一次逻辑调用的多个重试 Attempt。
- Trace 总耗时依赖创建、完成时间推导，没有独立根 Span。

### 3.2 当前模型调用记录

`LLMCallRecord` 已记录：

- `call_id`
- `trace_id`
- 上下文类型和上下文 ID
- Endpoint
- Model
- 状态
- 请求和响应
- 总耗时
- 错误
- 创建和完成时间

可复用价值：

- 可以作为 Model Span 的采集来源。
- 已有输入 Token、输出 Token和总 Token。
- 前端已有单次调用耗时、Token 和输出速度展示逻辑。

当前限制：

- 没有 TTFT。
- 没有缓存 Token 和推理 Token 的统一字段。
- 模型 Provider、模型配置版本和 Agent 版本没有完整快照。
- 输出速度当前使用总耗时估算，不能区分首 Token 前等待时间和实际生成时间。
- 请求和响应直接保存完整内容，尚未统一执行敏感数据策略。

### 3.3 当前工具和 AINA 调用

当前工具和 AINA 调用已经记录：

- 能力类型和能力 ID
- `call_id`
- 函数名
- 输入参数
- 返回结果
- 调用耗时
- 错误码、错误信息和是否可重试

项目中已经存在：

- Tool `version`
- AINA Manifest `version`
- AINA Installation `installed_version`
- Tool 超时和重试配置

可复用价值：

- 可以形成 Tool Span、AINA Span 和版本分析维度。
- 已有错误分类可作为 Error Event 标准化输入。

当前限制：

- 工具重试发生在 Gateway 内部，没有逐次记录 Attempt。
- 多个 Tool Call 当前主要按顺序执行，尚未形成并行 Span 表达。
- 工具调用的 Trace 属性中没有稳定保存工具版本。
- AINA 作为 Agent 还是 Tool 的分析口径尚未定义。

### 3.4 当前错误能力

当前已有统一的 `PlatformError`，包含：

- 错误码
- 错误信息
- HTTP 状态码
- 是否可重试
- 错误来源
- 用户提示
- Debug 信息

HTTP 异常响应中也会返回一个请求级 Trace ID。

可复用价值：

- 可以作为 Error Event 错误码、来源和可重试字段的基础。
- 已有模型、工具和存储错误分类。

当前限制：

- HTTP 请求的 `request_*` 标识与 Agent 的 `trace_*` 标识没有统一关系。
- 错误只存在于异常响应或 Trace Event 中，没有独立的错误明细和聚合模型。
- 无法按错误指纹、错误码、来源、Agent、模型和工具形成错误趋势。
- 错误不能稳定跳转到唯一异常 Span。

### 3.5 当前日志能力

项目当前使用 Python 标准日志，部分异常日志会附加 `trace_id`。

当前限制：

- 没有统一日志上下文。
- 没有 `span_id`。
- 普通日志不能保证带 Trace 标识。
- 没有日志采集、索引和查询接口。
- 没有从 Span 查看关联日志的前端入口。

### 3.6 当前存储能力

项目使用 MySQL 作为权威存储、Redis 作为缓存和运行锁。当前业务记录采用通用表结构：

- `id`
- `payload` JSON
- `updated_at`

持久化 Repository 启动时会加载全部 Trace 和 LLM Call 到进程内存；增加 Trace Event 时会重新保存整条 Trace。

可复用价值：

- MySQL 和 Redis 基础设施可以继续使用。
- Repository 抽象允许逐步增加专用存储实现。

当前限制：

- 无法通过普通索引高效完成 Agent、模型、工具、状态和时间范围检索。
- Trace 增长会导致 JSON 更新放大。
- 全量加载不适合长期保留可观测明细。
- 不适合实时计算 P50、P95、P99、趋势和多维聚合。
- 当前没有数据保留、归档和清理机制。

### 3.7 当前前端能力

Debug 页面已具备：

- Trace 列表
- 按会话分组
- Trace 状态
- Trace 事件时间线
- 模型调用列表和详情
- 请求、响应、耗时和 Token 展示
- 从 Chat 运行结果跳转 Trace

可复用价值：

- 可以继续作为“运行诊断”模块的基础页面。
- 现有组件和 API 调用可以逐步迁移到新的 Trace/Span 接口。

当前限制：

- Trace 列表没有服务端分页和完整筛选。
- 调用关系以事件列表展示，不是树形或瀑布图。
- 没有错误中心、日志面板和分析页面。
- 当前用户和租户固定为 `anonymous/default`。
- 没有反馈入口和运营页面。

### 3.8 当前用户、租户和反馈关联基础

当前项目已有：

- Conversation `user_id`、`tenant_id`
- Message `id`、`trace_id`
- ChatResponse `message_id`、`trace_id`
- AINA 和 Tool 标识

这些字段可以支持 Feedback 绑定到具体 Assistant Message。

当前限制：

- 用户身份目前不是统一由可信认证中间件提供。
- 匿名用户没有稳定身份规则。
- 没有部门、用户类型和组织属性。
- 没有 Agent 权限用户清单，无法计算渗透率分母。
- 没有 Feedback 和 Feedback Case 数据。

## 5. 总体开发要求

### 5.1 标识和上下文要求

系统应建立统一标识体系：

| 标识 | 用途 |
| --- | --- |
| `request_id` | 一次外部用户或 API 请求的业务标识 |
| `trace_id` | 一次端到端 Agent 执行链路 |
| `span_id` | Trace 中一个可独立计时和诊断的执行节点 |
| `parent_span_id` | Span 的直接父节点 |
| `logical_call_id` | 一次逻辑模型或工具调用，用于归并多个 Attempt |
| `attempt_id` / `attempt_no` | 一次实际重试尝试 |
| `conversation_id` | 会话 |
| `message_id` | 具体用户或 Assistant 消息 |
| `error_event_id` | 标准化错误明细 |
| `feedback_id` | 用户反馈 |

需要在详细设计阶段明确：

- `request_id` 是否直接使用用户消息 ID，还是单独生成。
- HTTP Trace 与 Agent Trace 是否为同一个 Trace，或采用父子 Trace/Span。
- 外部传入 Trace 标识是否信任，以及如何防止用户伪造后越权查询。

### 5.2 Trace/Span 数据要求

每个 Span 至少应具备：

- Trace 和 Span 标识
- 父 Span 标识
- Span 类型和名称
- 状态
- 开始时间、首输出时间、结束时间和耗时
- 用户、租户、会话、请求和消息标识
- Agent/AINA ID 和版本
- Provider 和模型
- Tool ID 和版本
- 输入输出摘要或 Payload 引用
- Token 信息
- 错误信息
- 重试和并行关系
- 创建来源和采集版本

建议 Span 类型至少包括：

- `agent`
- `model`
- `tool`
- `aina`
- `internal`

### 5.3 采集可靠性要求

- 可观测数据采集失败不得阻塞 Agent 主业务。
- Trace 创建、Span 上报和聚合写入应具备降级策略。
- 采集失败需要有内部计数和日志，不能静默丢失。
- Agent 执行结果成功与可观测数据写入成功应分开判定。
- 允许短暂异步延迟，但必须满足明细 1 分钟内可查询目标。
- 应定义进程退出、服务重启和队列积压时的数据处理策略。

### 5.4 数据存储要求

当前通用 JSON 表不应直接作为完整分析方案。详细设计至少需要评估：

1. Trace/Span 明细使用专用关系表还是接入标准 Trace 后端。
2. 聚合指标使用 MySQL 聚合表、分析数据库还是时序存储。
3. 原始日志接入现有日志平台还是建设最小日志索引。
4. 超大 Prompt、响应和工具输出使用 NAS/S3 等外部 Payload 存储。
5. 热数据、冷数据和删除任务的保留策略。

无论采用哪种实现，必须支持：

- 按租户和时间范围建立查询边界。
- 按 Trace、Span、Agent、版本、模型、工具和状态检索。
- 分页查询。
- 明细和聚合分离。
- 避免服务启动时加载全部可观测历史数据。

### 5.5 数据安全要求

- 用户和租户必须来自可信认证上下文，不能由普通客户端自由指定。
- Trace、Span、LLM Call、日志、反馈和运营接口必须统一鉴权。
- 普通用户只能访问自己的对话和 Trace。
- Agent 负责人只能访问其负责 Agent 的数据。
- 租户管理员只能访问本租户数据。
- 平台管理员权限需要单独授予和审计。
- Prompt、模型响应、工具参数、工具响应和日志必须统一经过敏感信息策略。
- API Key、Token、Cookie、Authorization、密码和密钥不得以明文进入分析存储。
- 用户输入文本需要考虑个人信息和企业敏感信息，而不能只识别密钥模式。
- LLM Call 现有历史数据需要评估是否迁移、脱敏或清理。

## 6. 开发任务拆分

### 6.1 阶段 A：需求口径和架构决策

#### DR-FND-001 统一指标字典

- 优先级：P0
- 来源：IR-01、IR-02 全部分析 SR
- 工作内容：
  - 定义有效请求、成功、失败、取消和审批中状态。
  - 定义 Agent 单轮耗时、模型总耗时、TTFT 和工具耗时。
  - 定义 Token 各字段。
  - 定义超时率、重试次数和调用步骤数。
  - 定义活跃、新增、权限用户、渗透和留存。
  - 为指标字典增加版本。
- 验收：
  - 相同输入样例在不同页面和导出结果中计算一致。
  - 每个指标具有分子、分母、时间窗口、去重键和排除条件。

#### DR-FND-002 统一身份和权限模型

- 优先级：P0
- 来源：SR-SEC-001、SR-SEC-003
- 工作内容：
  - 将可信认证主体注入 `RequestActor`。
  - 停止信任普通请求参数中的用户和租户。
  - 定义普通用户、Agent 负责人、运营、租户管理员和平台管理员。
  - 定义 Agent 数据归属关系。
- 验收：
  - 用户无法通过修改参数访问其他用户或租户数据。
  - Trace ID 被猜中时仍需通过资源权限校验。

#### DR-FND-003 可观测存储和日志方案

- 优先级：P0
- 来源：IR-01 边界约束和性能目标
- 工作内容：
  - 完成 Trace/Span、指标、日志和 Payload 存储选型。
  - 完成容量估算、索引方案、保留周期和归档策略。
  - 明确是否采用 OpenTelemetry 标准和现有可观测后端。
- 验收：
  - 方案能够解释 1 分钟明细时效、5 分钟聚合时效和 3 秒查询目标。
  - 方案不依赖全量内存加载。

#### DR-FND-004 Agent 和版本口径

- 优先级：P0
- 来源：SR-PERF-005、IR-01 版本对比场景
- 工作内容：
  - 明确平台主 Agent 与 AINA 的关系。
  - 定义 Trace 中 Agent ID、Agent 版本和配置版本。
  - 定义 Tool 和模型版本快照。
- 验收：
  - 历史 Trace 不因当前配置变化而改变分析维度。

### 6.2 阶段 B：Trace/Span 采集底座

#### DR-OBS-001 统一 Trace 上下文

- 优先级：P0
- 来源：SR-OBS-001
- 工作内容：
  - 统一 HTTP、Chat、Agent、AINA 和远程 Tool 的上下文。
  - 明确上下游 Header 和协议字段。
  - 将 Trace 上下文注入日志和异步任务。
- 验收：
  - 一次用户请求在所有支持的内部和远程节点使用同一关联上下文。

#### DR-OBS-002 Span 生命周期模型

- 优先级：P0
- 来源：SR-OBS-002、SR-OBS-003
- 工作内容：
  - 新增 Span 开始、完成、失败和取消语义。
  - 建立父子关系、逻辑调用和 Attempt。
  - 保证结束状态幂等。
- 验收：
  - 正常、异常和中断执行都能形成结构完整的调用树。

#### DR-OBS-003 Agent Span 采集

- 优先级：P1
- 来源：SR-PERF-001
- 工作内容：
  - 创建根 Agent Span。
  - 记录请求接收、最终响应、Agent/AINA、版本、迭代数和步骤数。
  - 记录审批暂停和恢复。
- 验收：
  - Agent 单轮耗时符合需求定义。

#### DR-OBS-004 Model Span 采集

- 优先级：P1
- 来源：SR-PERF-002
- 工作内容：
  - 将 LLM Call 与 Model Span 关联。
  - 记录 Provider、模型、配置版本、流式状态、TTFT、总耗时和 Token。
  - 区分空响应、供应商错误、限流和超时。
- 验收：
  - 流式调用可以查询首 Token 时间和响应结束时间。
  - Model Span 与 LLM 请求详情一一对应。

#### DR-OBS-005 Tool 和 AINA Span 采集

- 优先级：P1
- 来源：SR-PERF-003
- 工作内容：
  - 采集 Tool、AINA 和内建工具 Span。
  - 记录版本、输入、输出、状态和耗时。
  - 将每次重试记录为独立 Attempt。
  - 支持未来并行工具调用的关系表达。
- 验收：
  - 可以区分逻辑调用次数和实际 Attempt 次数。
  - 超时率能够从明细稳定计算。

#### DR-OBS-006 采集降级和完整性监控

- 优先级：P0
- 来源：IR-01 边界约束 1、成功指标
- 工作内容：
  - 将可观测写入与 Agent 业务结果解耦。
  - 定义缓冲、批量、重试和丢弃策略。
  - 记录采集成功率、覆盖率和字段完整率。
- 验收：
  - 模拟可观测存储故障时，Agent 仍能完成请求。
  - 采集丢失能够被监控发现。

#### DR-OBS-007 统一 Payload 安全处理

- 优先级：P0
- 来源：SR-SEC-002
- 工作内容：
  - 将 Trace Event 和 LLM Call 纳入同一脱敏流程。
  - 支持摘要、截断和外部 Payload 引用。
  - 定义不同角色能否查看完整内容。
- 验收：
  - 密钥和认证信息不会出现在 Trace、LLM、日志和反馈查询结果中。

## 7. 概念数据对象

| 对象 | 主要职责 |
| --- | --- |

## 10. 非功能开发要求

### 10.1 性能

- 明细数据在请求完成后 1 分钟内可查询。
- 聚合数据延迟不超过约定的 5 分钟。
- 常规 Trace、Error 和 Feedback 查询 3 秒内返回。
- 所有列表使用服务端分页。
- 不允许在浏览器端获取全部历史明细后聚合。

### 10.2 可用性

- 可观测采集故障不阻塞 Agent 主流程。
- Feedback 提交故障不影响对话记录和响应展示。
- 聚合任务失败可以重试和补算。
- Trace 和指标查询故障不影响 Chat。

### 10.3 一致性

- Trace 和 Span 状态转换必须幂等。
- 重复用户事件不能重复计数。
- 重复 Feedback 必须更新原评价。
- 聚合结果可以从明细重算。

### 10.4 安全

- 全部查询必须经过可信身份和资源权限校验。
- 敏感信息在进入可观测存储前处理。
- 访问完整 Prompt、响应和日志需要额外权限。
- 负责人、状态和处理结论的修改需要审计。

### 10.5 数据治理

- 明确 Trace、Span、Error、Log、Payload、Feedback 和聚合数据保留周期。
- 明确用户删除、账号合并和租户删除对历史数据的影响。
- 明确过期 Trace 与仍保留 Feedback 之间的页面提示。
- 指标定义变更后应保留口径版本。

| M0 | 指标字典、身份权限、存储和版本方案 | 无 |

## 13. 首期最小闭环建议

### 13.1 IR-01 最小闭环

1. 用户发起 Chat 请求。
2. 系统生成完整 Trace 和根 Agent Span。
3. 模型和工具调用生成子 Span。
4. 模型或工具失败时生成 Error Event。
5. 错误中心可以查询错误。
6. 用户进入 Trace 后自动定位异常 Span。
7. 用户可以查看脱敏后的输入、输出、错误和关联日志。
8. 分析页可以查看对应 Agent、模型和工具的耗时、成功率和 Token。

### 13.2 IR-02 最小闭环

1. 用户对具体 Assistant Message 点赞或点踩。
2. 点踩可以选择原因并填写说明。
3. Feedback 自动关联用户、租户、会话、消息、Agent 和 Trace。
4. Agent 负责人可以查询和处理 Feedback。
5. 负面反馈可以回溯对话和调用链。
6. 平台可以统计反馈、活跃、请求量、Agent 渗透和基础留存。

## 14. 编码前待确认事项

以下问题会直接影响数据模型和实现路径，必须在进入对应模块开发前确认：

1. 原始需求中的 Agent 是否等同于 AINA，还是同时包含 Unibot 主 Agent。
2. `request_id` 是否直接使用用户 Message ID。
3. HTTP 请求 Trace 与 Agent Trace 是合并还是父子关系。
4. 有效请求是否包含失败、取消、审批中、定时任务和 Debug 请求。
5. Agent 版本是 Manifest 版本、安装版本、发布版本还是配置快照版本。
6. 模型配置变化是否需要生成独立配置版本。
7. 用户和租户认证信息由哪个系统提供。
8. Agent 负责人和租户管理员由哪个系统维护。
9. 部门和用户类型从哪里获取。
10. Agent 权限用户清单从哪里获取。
11. 匿名用户使用 Cookie、设备 ID、会话 ID 还是其他方式识别。
12. D1、D7、D30 使用自然日、滚动还是区间留存。
13. Trace、日志、Payload、Feedback 和指标的保留周期。
14. Prompt、模型输出和工具结果是否允许全文保存。
15. 哪些角色有权限查看完整 Prompt、响应和日志。
16. 是否已有企业日志平台、Trace 平台或指标平台可以复用。
17. 预计日请求量、峰值 QPS、平均模型调用数和平均工具调用数。
18. 用户删除或账号合并后，历史反馈和运营指标如何处理。

## 15. 明确不在本期的内容

按照原始需求，本期不包括：

- 基于大模型的自动根因分析
- 自动修复 Agent 配置或代码
- 完整告警平台
- 回答内容质量自动评测
- Agent A/B 实验平台
- 成本预算和配额控制
- 跨企业、跨平台全链路追踪
- 自动生成用户反馈回复
- 自动关闭或自动修复 Feedback Case
- 全量情感分析
- 用户画像推荐
- 精细化营销和消息触达
- 商业化计费
- 完整客户工单系统
- 因果分析和增长实验平台

## 16. 最终结论

本项目可以复用现有 Trace、LLM Call、Message、AINA/Tool 版本、错误模型、脱敏工具和 Debug 页面，但不能把现有 Trace JSON 和前端本地统计直接扩展为最终方案。

开发工作的核心不是单纯增加几个分析页面，而是先完成以下四项基础改造：

1. 建立可信用户身份和数据权限。
2. 将平铺 Trace Event 升级为正式 Trace/Span 模型。
3. 将业务主链路与可观测写入解耦。
4. 建设可检索的明细存储和统一聚合口径。

完成上述基础后，IR-01 的诊断和性能分析、IR-02 的反馈与运营分析才能共享一致的请求、用户、Agent、版本和指标数据，并形成需求中定义的完整闭环。
